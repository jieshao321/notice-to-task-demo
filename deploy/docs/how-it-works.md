# 它是怎么工作的

## 一句话

**一个单智能体 + 一段 241 字的规则，没有编排、没有工作流、没有多智能体。**

## 为什么不用工作流

AgentArts 支持工作流编排，我们一开始也画过六层流程图（入口 → 解析 → 抽取 → 校验 → 生成 → 交付）。

后来发现：**如果每一层都要写节点、连边、处理异常，团队一周 5 小时根本跑不完。**

所以我们做了一个取舍——**把六层逻辑压进一个智能体的提示词里**，用规则约束代替流程约束。

| 层 | 工作流做法 | 我们现在的做法 |
|---|---|---|
| 入口 | 一个节点接收输入 | 对话页直接接收文字/截图/PDF |
| 解析 | OCR 服务 + 文本抽取节点 | 模型直接读（多模态） |
| 抽取 | 结构化输出节点 + schema | 提示词规则 1/3/4 约束 |
| 校验 | 规则引擎节点 | 提示词规则 2 + 「待确认」机制 |
| 生成 | 模板节点 + 润色节点 | 模型一次性生成 |
| 交付 | 发布节点 | 演示页呈现 |

**结果**：代码量从「一个工作流项目」降到「一段提示词」，团队能在一周 5 小时里把它跑通、改 12 版、测 20 条用例。

## 数据流

```
用户贴入通知（文字 / 截图 / PDF）
        ↓
AgentArts Playground / 运行时 API
        ↓
系统提示词（241 字，五条规则）
        ↓
DeepSeek-Chat
        ↓
八行任务卡（JSON）
        ↓
前端渲染 → 点任意一行可回链原文 → 回答待确认 → 回写更新
```

## 实测调用成本

单次调用（2026-11-16，平台「输出」面板）：

```
输入：46,575 tokens
输出：459 tokens
总计：47,024 tokens
```

**输入的 99% 是平台注入的系统上下文**（AgentArts 的运行时指令、工具定义等），不是用户那 543 字通知。

所以：

- 换一条更长的通知，输入 token 几乎不变
- 成本主要来自「进入平台」这件事本身，不是内容长度
- 单条成本约 0.03 元（DeepSeek 定价）

## 「待确认」机制

这是产品的核心设计，也是最容易做错的地方。

**做法**：

1. 提示词规则 1 要求：原文没写的，值填 `null` **并放进待确认数组**
2. 前端把待确认渲染成「追问清单」，每条带一个输入框
3. 老师回答 → 点「确认回写」→ 任务卡对应行当场更新

**一个真实例子**（演示视频里的那条通知）：

原始输出有 5 条待确认：

1. 申请表份数
2. 是否需盖章
3. 各分院补评名额及等级
4. 是否需家庭重大变故证明材料
5. 公示时长及方式

老师答完 5 条后，任务卡从「5 项待确认」变成「5 项全部已确认，任务卡闭合」，右上角 `8/8 行已明确 · 0 项待确认`。

**规则行下方会多出绿字**：

```
（已确认）每院 2 个名额
（已确认）需附变故证明
（已确认）公示五个工作日
```

**这就是「工件」和「问答」的区别**——问答给你的是一段话，工件给你的是一份能直接发出去、能逐条核对的东西。

## 一个真实的产品边界

通知原文有一处**内部矛盾**：

> 「2026 年春季学期**新增**被认定为家庭经济困难的学生」
> 「以秋季学期评定结束后家庭遭遇**重大变故**、导致家庭经济特别困难的学生为主」

两句话指向不同人群。模型把这条矛盾放进了待确认，但**不会替你判断哪个对**。

**这是设计意图**：判断谁是「该补评的人」是辅导员的职责，不是模型的。
