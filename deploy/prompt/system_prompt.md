# 系统提示词

AgentArts 智能体 `managed-notice-to-task` 的完整系统提示词。

**全文 241 字，五条规则。没有 schema，没有 few-shot 示例。**

## 原文

```
1. 只从原文抽取，不推断、不补全；原文没写的，值填 null 并放进「待确认」。
2. 截止时间保留原文表述，同时给出换算后的具体日期；无法换算的写进待确认。
3. 材料要逐条列，标注份数与是否盖章。
4. 原文提到附件时，在材料里注明「见附件」并列出附件名。
5. 不要输出任何解释性文字，不要加 Markdown 代码块标记。
```

## 为什么只有五条

我们试过写长提示词——加 JSON schema、加 few-shot 示例、加字段说明。结果是：

**提示词越长，模型越容易在「原文没写」的地方开始编。**

比如通知里只写「材料交到辅导员处」，提示词如果列了「交到哪」的三种可能格式，模型就会往里填一个看起来合理的地址。

**所以我们把提示词砍到只剩「不许做什么」**：

| 规则 | 防的是什么 |
|---|---|
| 规则 1 | 编造字段（最常见、最致命的错误） |
| 规则 2 | 把「3 月 23 日前」直接当日期，不换算年份 |
| 规则 3 | 把「一式两份、要盖章」合并成一句，漏掉可核对的细节 |
| 规则 4 | 附件名丢了，老师不知道该找什么表 |
| 规则 5 | 输出裹一层 `` ```json `` 或「好的，我来帮您分析」 |

**结构（八行任务卡）不写在提示词里，由模型在规则约束下自然收敛。**

这是刻意的取舍：**用规则约束行为，而不是用 schema 约束格式**。

好处是换模型不用改提示词；代价是输出结构依赖模型的理解力，弱模型会跑偏（我们试过一个 7B 的小模型，八行只给出四行）。

## 一个具体例子

输入片段：

> 学生在3月23日前提交《本专科生国家助学金申请表》（附件）至辅导员处。

模型输出：

| 字段 | 值 |
|---|---|
| 截止 | 学生提交申请表 · 原文「3 月 23 日前」→ **2026-03-23** |
| 材料 | 《本专科生国家助学金申请表》（见附件）；份数：**null**；是否盖章：**null** |

「份数」「是否盖章」原文没写，**填 null 并进待确认，不猜**。

后续由老师回答「一式两份」「需盖章」，任务卡当场更新为：

> 《本专科生国家助学金申请表》（见附件）；份数：**1 份**；需盖章；材料要素已齐

## 已知的坑

1. **两处「3 月 23 日」是不同的人**——学生提交截止和辅导员上报截止都写 3/23，模型一开始会合并。提示词加不上规则（这是语义问题），靠「截止」行分三行（学生/辅导员/分院）解决。
2. **「新增困难生」vs「重大变故困难生」**——同一份通知里两种表述，指的是不同人群。模型能识别出矛盾并放进待确认，但不会自动判断哪个对。
3. **待确认没有字段级锁定**——回答一条可能清空整个数组，见 README 的「已知局限」。
