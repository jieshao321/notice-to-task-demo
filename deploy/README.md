# 通知落地助手 · Notice-to-Task

把一个几十字的通知，变成一份能直接发班的任务包。

**在线演示**：https://jieshao321.github.io/notice-to-task-demo/
（界面演示，结果为预置数据；真实解析见下方「怎么运行」）

---

## 它解决什么问题

高校辅导员（或辅导员助理）每周要处理 3—5 条学校通知：评奖、选课、实习、考试。一条 1200 字的通知，他们要：

读三遍 → 摘要素 → 写成群发文案 → 发到 4 个群 → 挨个私聊没交的 → 建表登记

**访谈中位数：一条通知 60 分钟**，其中约 40 分钟花在「读懂 + 转写」上。

已有的产品（教务问答机器人、校园百事通小程序）都停在「回答」这一层——**没有人做「辅导员拿到通知之后的那一段」**。

## 它产出什么

一条通知进去，八行任务卡出来：

| 行 | 内容 |
|---|---|
| 事项 | 这条通知到底是干什么的 |
| 对象 | 谁要参与 |
| 条件 | 参与门槛（逐条列） |
| 截止 | 时间节点（保留原文表述 + 换算后的日期） |
| 材料 | 交什么、几份、要不要盖章 |
| 交到哪 | 线下地址 / 线上渠道 |
| 找谁 | 联系人 |
| 待确认 | 原文没写的，标出来问人，不猜 |

外加五件工件：群发文案 · 催办计划 · 核验清单 · 未交名单 · 日历提醒。

## 三条硬约束

1. **只从原文抽取**——不推断、不补全。原文没写的填 `null`，放进「待确认」。
2. **每条结论回链原文**——点任意一行，能高亮回到通知里的那句话。
3. **不自动发消息**——发出去的责任永远留在人这一侧。

## 怎么运行

后端是华为云 **AgentArts** 上的一个单智能体，配置极简：

| 项 | 值 |
|---|---|
| 模型 | `deepseek/deepseek-chat` |
| 环境 | `notice-env` |
| 系统提示词 | **241 字，五条规则**（见 [`prompt/system_prompt.md`](prompt/system_prompt.md)） |
| 工具 | 无 |
| Skill | 无 |

**没有编排、没有工作流、没有多智能体。** 一个模型 + 一段规则 + 一个环境。

实测单次调用：输入 46,575 tokens / 输出 459 tokens（2026-11-16，见平台截图）。
其中输入的大头是平台注入的系统上下文，不是用户那 543 字通知。

## 评测结果

20 条真实学校通知（已清洗），逐条人工判定六个字段。

| 指标 | 结果 |
|---|---|
| 首测通过 | **19 / 20** |
| 复测通过 | **17 / 18** |
| 字段级准确率 | **100%**（102 / 102 个字段） |
| 硬信息错误 | **0**（日期、金额、份数、盖章要求） |
| 单条出卡用时 | 中位 **8.9 秒** |

原始记录见 [`eval/`](eval/)（`cases.json` + `results.csv`）。

### 唯一未通过的那条（case 7）

原文只有一句：「工作底稿原文·带附件（附件1《XX申请表》、附件2《汇总表》）」

- 附件本体没有随输入提供
- 模型**正确识别了两个附件名，没有编造任何字段**
- 但「字段齐全」这一项要求给出完整清单，附件不在，给不出 → 判不通过

**归因：素材缺失，不是抽取能力问题。** 这也是产品的一个真实边界——**附件要跟通知一起给**。

## 已知局限

1. **待确认没有字段级锁定**——回答一条，可能把整个待确认数组清空，而不是只清掉那一条。
2. **图片输入未纳入复测**——20 条用例中 2 条是图片（OCR 路径），复测时素材未随包提供，这两条没跑。
3. **第 5—8 步未实现**——催办计划、核验清单、未交名单、日历提醒目前是设计稿，界面有位置但未接真实数据。
4. **没有公开 Web 入口**——AgentArts 当前版本的发布出口只支持 IAM 认证的 API/MCP，不提供免登录网页。
